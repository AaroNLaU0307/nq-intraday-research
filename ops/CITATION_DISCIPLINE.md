## 条款

> **新增一条路径引用时，被引字节必须已存在。**
> **唯一例外**：引用方作者在**写下的当时**就显式声明其为提案（`PROPOSED`），
> 登入 `tests/test_cited_records_exist.py` 的 `_KNOWN` 并附提案出处。

---

## 为什么把声明义务放在写入时刻

`PROPOSED_NOT_YET_EXISTING` 与 `CITED_BUT_NEVER_EXISTED` **在磁盘上完全同形**：
两者都是「路径不存在、git 全历史无增无删」。事后没有任何机械规则能分开它们。

但**在写入的那一刻，意图只有作者知道，且声明成本为零**。把声明义务放在唯一
拥有该事实的时点，是消除这个不可判定性的唯一不费钱的位置；事后任何规则都是在猜。

**这条不是理论。** 2026-08-27 它被实测证成：三条路径因为当初没有声明为提案，
两天到三天之后被 builder 误分类为「凭空引用」，并据此送进一个决裁席位——
席位是盲席、拿不到那些引用行，只能按 builder 的分类推理，于是白裁了一件。
逐条读引用行之后，三条全部是提案（一个是被否决选项的假设文件，一个是已在册恢复
路径的落盘目标，一个字面写着「是否新建……工程建议：建」）。详见
`ops/CORRECTION_CLASS_B_WERE_PROPOSALS_2026-08-27.md`。

**声明成本为零的那一刻没有付，代价在两天后由一个复审席位付了。**

## 机械件与人件的分工

```
机械件（已就位）  tests/test_cited_records_exist.py
                  新增的未登记悬空引用 -> 红
                  它拦得住「引用了不存在的字节」这件事本身

人件（本条款）    它拦不住的那一半：登记 _KNOWN 时必须附理由；
                  分类为 PROPOSED 时必须附提案出处（哪份文书、哪一节）
```

守卫只能问「这条悬空引用登记了吗」，不能问「登记的分类对不对」。
**分类的正确性由本条款在写入时刻保证，不由守卫在事后保证。**

---

## 覆盖范围的诚实边界

机械件的正则只认 **正斜杠 `ops/…` 形态**。反斜杠路径与裸文件名不在覆盖内。
因此「钉死、不会增长」这句话的准确表述是：**在这一形态上不会增长。**

这个边界是有意的，且与裁定 C1 是同一把剑的两面——C1 规定的禁区标记**保留裸文件名**，
正是为了让它不被读成引用。**正则忽略什么，标记就被允许说什么。**

## 落地检查清单（写入任何 `ops/` 文档时）

```
1. 我写的这条路径，字节现在存在吗？        存在 -> 完成
2. 不存在，那它是提案吗？                  不是 -> 不要写这条路径
3. 是提案 -> 在同一句里写明它是提案
           -> 登入 _KNOWN，分类 PROPOSED_NOT_YET_EXISTING
           -> 在登记条目的注释里写明提案出处（文书 + 节号）
```

第 3 步的三件必须同一次改动完成。**只做前两件而不登记，下一次全套就会红**——
那是守卫在替本条款把关，而不是本条款可以省略。

## 证伪条件（裁定原文）

> 若 `PROPOSED` 声明例外在登记册里增长到常态化（条款沦为仪式），条款需重设计。

**当前基线**：`_KNOWN` 里 `PROPOSED_NOT_YET_EXISTING` 共 5 条
（S5 提出的文件名、S5 选项 RENAME_OUT 的举例路径，加上本次更正后重分类的三条）。
若该数持续增长而无一转为实际存在，即触发本证伪条件。
